# 内存安全：恢复调度与堆余量

状态：0.7.0 设计稿（实现见 `lib/engine.js` 的恢复循环与 `/state`）
日期：2026-10-29
适用版本：dsh-pause-resume 0.7.0 / DSH 0.2.x

一句话：恢复一个会话要把整份 transcript 反序列化进宿主堆，所以恢复节奏必须由「还能放下多少」决定，
不能只看「还有多少要恢复」。

## 1. 为什么会崩

化石点不在插件里，在宿主的 V8 上。恢复一个会话时，Harness 会把该会话的整份 transcript 读进内存并
反序列化；一个大会议话单份就是 GB 级，而宿主 V8 大约 4 GB 封顶。撞到上限时进程不会抛出一个可捕获
的异常，而是直接死掉：

```
FATAL ERROR: MarkCompactCollector: young object promotion failed
```

实测 2026-10-29 两次：

| 次序 | 时间 | pid | 运行时长 | 堆峰值 | 当时在做 | 日志 |
| --- | --- | --- | --- | --- | --- | --- |
| 第一次 | 2026-10-29 | 91126 | 64 分钟 | 3.65 GB | 长时间批量恢复 | `~/Library/Logs/DeepSeek Harness/crash-*-host.log` |
| 第二次 | 2026-10-29 | 61989 | 恢复 15 个会话后 15 分钟 | 3.58 GB | 恢复 15 个会话 | `~/Library/Logs/DeepSeek Harness/crash-*-host.log` |

两次都不是 OOM killer，也不是磁盘或网络：堆一直在涨，涨到 V8 无法完成一次新生代对象晋升。这就是
「恢复越快、越整齐，越容易崩」的原因——并发恢复把多份 transcript 同时摊在堆上。

## 2. 恢复调度

四条规则，按顺序生效：

1. **只恢复本次崩溃确实中断的会话。** 历史会话、已完成的会话、正常结束的会话都不碰。这一条 0.6.x 已有，
   不是本轮新增；本轮新增的是下面三条。
2. **逐步恢复，小的先走。** 会话按 transcript 体积从小到大排队，轻会话先恢复，大会话排在最后。
   轻会话一轮最多 `restoreConcurrency`（默认 2）个同时进行。
3. **大会话独占。** 体积 ≥ `restoreHeavyMB`（默认 12 MB 压缩转录）的会话进入独占段：一次只恢复一个，
   等它的 turn 结束，或等到 `restoreSettleMs`（默认 90 s）上限，再恢复下一个。
4. **堆余量闸门。** 每步恢复前读 `v8.getHeapStatistics()`；剩余余量低于 `restoreHeapReserveMB`
   （默认 700 MB）就不再挂载任何会话。没轮到的会话不加载转录（加载它正是闸门要避免的开销），
   只写入 `deferred` 记录，留给下次启动或手动恢复。

```
启动 / 重启
   │
   ├─ 读崩溃计划：只保留「崩溃时确有未完成 turn」的会话
   │
   ├─ 按压缩转录体积升序排队
   ▼
 还有下一个？ ── 否 ──► 收尾：归档本轮结果，计划关闭
   │是
   ├─ 体积 ≥ restoreHeavyMB ── 是 ──► 独占：等 turn 结束或 restoreSettleMs
   │
   ├─ 读 v8.getHeapStatistics()
   │      └─ 余量 < restoreHeapReserveMB ──► 停止本轮
   │                                          未轮到的：不挂载、不发送继续
   │                                          写 deferred 记录
   ▼
 挂载会话（已在挂载则跳过）
   │
   ▼
 发一条继续消息（只对「本次崩溃中断了 turn」的会话；请求 id 由计划与会话派生）
   │
   └─► 回到「还有下一个？」
```

顺序是有意的：先让轻会话把「人已经看到恢复在动」这件事做出来，再让大会话独占堆；闸门放在每一步之前，
所以最坏情况是「少恢复几个」，不是「恢复途中崩掉」。

## 3. `deferred` 与 `restartRecommended`

两个字段都在 `/state` 里，一个说「这次没轮到的」，一个说「建议你重启」。

**`deferred`**：本轮因堆余量闸门没有轮到、或没等到独占段结束的会话。每条至少说明是哪个会话、为什么
没轮到（余量不足 / 等独占会话 / 本轮已停）。只有同一份崩溃计划还成立时才有效：

* 被 deferred 的会话本轮完全没有加载，所以它不占堆；下次恢复时才挂载它的转录；
* 计划不关闭，行上留 `deferred` 记录并进 `attention`，按钮继续给 ▶；下一次恢复会重新挂载它，是否有
  未完成的 turn 仍由它自己的实时 turn 判定，不靠这一行猜；
* 不重发已经恢复过的会话，也不把 deferred 当成失败——它只是没做，不是做错了。

**`restartRecommended`**：本轮的恢复含大会话，或产生了 `deferred` 时为真，同时带本轮堆用量与原因。
它是一条建议，不是命令：

* 插件不因为该字段为真就做任何事，不退出、不重启、不卸载插件；
* 客户端据此显示「跑完这些任务后重启宿主」；
* 堆已经涨上去的部分不会自己还回来：GC 只会回收不再引用的对象，transcript 仍然被活着的会话引用。
  重启是唯一可靠地把堆还给操作系统的办法。

## 4. 配置

全部可选，均有默认值：

| 键 | 默认 | 作用 |
| --- | --- | --- |
| `restoreConcurrency` | `2` | 轻会话一轮内同时恢复的个数 |
| `restoreHeavyMB` | `12` | 压缩转录到这个体积即算大会话，进入独占段 |
| `restoreHeapReserveMB` | `700` | 堆余量低于它就停止本轮恢复 |
| `restoreSettleMs` | `90000` | 等大会话 turn 结束的上限 |

它们与既有的渐进恢复不是同一层，可以同时开：

* `restoreProgressive` / `restoreCapacity` / `restoreMaxCapacity` / `restoreCooldownMs` 限的是
  **上游模型请求并发**——防止网关被一批恢复同时打满；
* 本轮四键限的是**恢复期的堆与转录并发**——防止宿主被几份 transcript 同时撑爆。

前者管「外面扛不扛得住」，后者管「自己扛不扛得住」。关掉渐进恢复不影响内存安全这四键；关掉这四键
也不影响请求池。

## 5. 手动恢复的建议

* **大会话一次点一个。** 看 `/state` 的 `deferred`，先恢复小的；恢复一个大会话后等它的 turn 真正结束，
  再点下一个。
* **看到 `restartRecommended` 就安排重启。** 不是立刻，而是「跑完手上这些任务」之后：手上还有 turn、
  还有 job 在跑的时候重启，等于人为再制造一次这次要修的事故。
* **重启后不必再点。** 崩溃计划留在磁盘上，重启后按钮仍给 ▶；上一轮 deferred 的会话在这一轮重新排到队尾。
* **不要连续狂点。** 每次按都会重新走一遍闸门，堆不会因为按得勤就变大。

## 6. 为什么不自动重启宿主

* 重启是破坏性的：进程里所有 running turn、后台 job、终端、未落盘的东西都会一起没。插件只知道自己恢复
  了哪些会话，不知道用户手里还有什么，因此没有资格替用户按下这个开关。
* 这台宿主的生命周期归宿主：插件是装配在里面的一个 bundle，自行退出进程等于越权，且会让宿主的退出
  流程、会话落盘与桌面壳都绕开自己的路径。
* 崩溃已经发生过一次，第二次「为了干净堆而杀进程」会把「可恢复的慢」换成「不可恢复的丢」。
* 所以插件只把事实摆出来：堆多少、为什么、建议什么时候重启；按钮与字段都不假装自己能重启。

## 7. 跨平台

状态与日志全部走 `node:path` / `node:fs`，落在 `$DSH_HOME` 或 `~/.dsh` 下；不调用 shell，不依赖
`stat` / `du` / `ps` 等外部命令，所以体积判断与堆判断在三平台上是同一套代码。

* **macOS / Linux**：目录 `fsync` 语义存在，写入后对目录 fsync。
* **Windows**：没有目录 `fsync` 的等价物，降级为不 fsync（`lib/ledger.js` 已按此处理）；写入仍是
  临时文件 + `rename`。
* 跨进程互斥用 `session.lock` 文件，不用 POSIX 专有调用。

差异只有目录 fsync 与换行，没有平台专属的恢复路径。
